Database – Course 1

ملخص: Mahmoud Mohamed ✦ by Eng Ihap El-Galaly

المفاهيم الأساسية

  • Data (البيانات): حقائق معروفة ممكن تتسجل ولها معنى ضمني.
  • Information (المعلومات): بيانات اتعالجت وبقت في شكل ليه معنى.
  • Database: مجموعة منظمة من البيانات المترابطة، بتتدار بحيث المستخدم يشوف المجموعة كلها أو أي جزء منطقي منها كوحدة واحدة.
  • DBMS: برنامج/نظام بيسهّل إنشاء وصيانة قاعدة بيانات محوسبة.
  • Database System = الـ DBMS + البيانات نفسها (وأحياناً التطبيقات كمان).

أمثلة على تطبيقات قواعد البيانات

  • Enterprise Information:
    • Sales: العملاء، المنتجات، المشتريات
    • Accounting: المدفوعات، الإيصالات، الأصول
    • Human Resources: بيانات الموظفين، المرتبات، ضرائب الرواتب
  • Universities: التسجيل، الدرجات
  • Airlines: الحجوزات، المواعيد
  • Document databases
  • Navigation systems: أماكن الاهتمام + المسارات الدقيقة للطرق والقطارات والباصات

Data Model

بيوصف 3 حاجات:

  • البيانات والهيكل (data and structure)
  • العمليات (operations) اللي بتتعمل على الهياكل دي
  • القيود (constraints) اللي لازم الـ DB تلتزم بيها

أنواعه

  • Relational model
  • Entity-Relationship model (أساساً لتصميم الـ database)
  • Object-based models (Object-oriented و Object-relational)

Schemas versus Instances

  • Database Schema: وصف قاعدة البيانات (الهيكل + القيود).
  • Schema Diagram: عرض بياني لبعض جوانب الـ schema.
  • Database Instance: البيانات الفعلية المخزنة في لحظة معينة. بيتسمى كمان database state أو occurrence.
  • Database State: محتوى الـ DB في لحظة زمنية.

  • الـ Schema بيتسمى intension، والـ state بيتسمى extension.

أنواع الـ Schema

  • Logical Schema: الهيكل المنطقي الكلي (مثال: بنك فيه عملاء وحسابات والعلاقة بينهم). مشابه لـ type information لمتغير في برنامج.
  • Physical Schema: الهيكل الفيزيائي الكلي للـ DB.

Physical Data Independence

  • القدرة على تعديل الـ physical schema من غير تغيير الـ logical schema.
  • التطبيقات بتعتمد على الـ logical schema.
  • الواجهات بين المستويات والمكونات لازم تكون محددة كويس بحيث التغيير في جزء ما يأثرش بشدة على الباقي.

Data Definition Language (DDL)

مثال من الملف:

create table instructor (
  ID        char(5),
  name      varchar(20),
  dept_name varchar(20),
  salary    numeric(8,2))
  • DDL هو notation للتخصيص لتعريف الـ database schema.
  • الـ DDL compiler بيولّد مجموعة table templates بتتخزن في data dictionary.
  • الـ Data dictionary بيحتوي metadata (أي data about data) زي:
    • Database schema
    • Integrity constraints: مثل Primary key (الـ ID بيحدد المدرس بشكل فريد)
    • Authorization: مين يوصل لإيه

Data Manipulation Language (DML)

  • لغة للوصول للبيانات وتحديثها حسب الـ data model.
  • بتتسمى كمان query language.
  • Pure DML: بتستخدم لإثبات خصائص القدرة الحسابية وللـ optimization ← Relational Algebra
  • Commercial DML: بتستخدم في الأنظمة التجارية ← SQL (أكتر لغة تجارية استخداماً)
  • Procedural DML: المستخدم بيحدد إيه البيانات المطلوبة وإزاي يجيبها.
  • Declarative DML (Non-procedural): المستخدم بيحدد إيه المطلوب بس من غير ما يحدد إزاي. وهي أسهل في التعلم والاستخدام من الـ procedural.
  • الجزء من الـ DML الخاص باسترجاع المعلومات اسمه query language.

SQL Query Language

  • SQL nonprocedural.
  • الـ query بتاخد كمدخل جدول واحد أو عدة جداول وبترجع دايماً جدول واحد.
  • عشان تحسب دوال معقدة، SQL بتتضمن عادةً (embedded) في لغة أعلى مستوى.

Database Access from Application Program

  • SQL مش بتدعم أفعال زي: إدخال من المستخدم، إخراج على الشاشة، التواصل عبر الشبكة.
  • الحسابات والأفعال دي لازم تتكتب بـ host language زي C/C++ أو Java أو Python مع SQL queries مضمنة بتوصل للبيانات.
  • Application programs: البرامج اللي بتتفاعل مع الـ DB بالطريقة دي.

Database Design

  • Logical Design: تحديد الـ database schema. التصميم محتاج إننا نلاقي مجموعة "جيدة" من relation schemas.
  • Physical Design: تحديد التخطيط الفيزيائي للـ DB.

Database Engine

نظام الـ DB مقسم لـ modules كل واحد بيتعامل مع مسؤولية من مسؤوليات النظام. المكونات الوظيفية بتنقسم إلى: Storage Manager و Query Processor (و Transaction Management).

Storage Manager

  • Program module بيوفر الواجهة بين البيانات low-level المخزنة في الـ DB وبين application programs والـ queries.
  • مسؤول عن:
    • التفاعل مع OS file manager
    • التخزين والاسترجاع والتحديث الكفء للبيانات
  • مكوناته:
    • Authorization and integrity manager
    • Transaction manager
    • File manager
    • Buffer manager
  • بينفذ data structures كجزء من الـ physical implementation:
    • Data files: بتخزن الـ DB نفسها
    • Data dictionary: بتخزن metadata عن هيكل الـ DB (خصوصاً الـ schema)
    • Indices: بتوفر وصول سريع لعناصر البيانات؛ الـ index بيدي pointers للعناصر اللي بتحمل قيمة معينة

Query Processor

  • DDL interpreter: بيفسر أوامر DDL ويسجل التعريفات في data dictionary.
  • DML compiler: بيترجم أوامر DML لخطة تقييم (evaluation plan) من تعليمات low-level يفهمها الـ query evaluation engine.
    • بيعمل query optimization: يختار خطة التقييم الأقل تكلفة من بين البدائل.
  • Query evaluation engine: بينفذ التعليمات low-level اللي ولدها الـ DML compiler.

Transaction Management

  • Transaction: مجموعة عمليات بتؤدي وظيفة منطقية واحدة في تطبيق DB.
  • Transaction-management component: بيضمن إن الـ DB تفضل في حالة consistent (صحيحة) رغم أعطال النظام (انقطاع كهرباء، crash في نظام التشغيل) وفشل الـ transactions.
  • Concurrency-control manager: بيتحكم في التفاعل بين الـ transactions المتزامنة لضمان consistency الـ DB.

Database Architecture

  • Centralized databases: من core لعدة cores، ذاكرة مشتركة.
  • Client-server: جهاز server واحد بينفذ الشغل نيابة عن عدة أجهزة clients.
  • Parallel databases: many cores shared memory • Shared disk • Shared nothing
  • Distributed databases: توزيع جغرافي • عدم تجانس في الـ schema/data

Database Applications

  • Two-tier architecture: التطبيق موجود على جهاز الـ client، وبيستدعي وظائف الـ DB system على جهاز الـ server.
  • Three-tier architecture: جهاز الـ client بيعمل كـ front end ومفيهوش أي database calls مباشرة.
    • الـ client بيتواصل مع application server (غالباً عن طريق forms interface).
    • الـ application server بدوره بيتواصل مع الـ database system للوصول للبيانات.

Database Administrator (DBA)

  • Routine maintenance

Chapter 2: Intro to Relational Model

مصطلحات الجدول

  • Attributes (columns) = الأعمدة
  • Tuples (rows) = الصفوف

Attributes

  • مجموعة القيم المسموحة لكل attribute اسمها domain of the attribute.
  • قيم الـ attributes (عادةً) لازم تكون atomic، أي indivisible (غير قابلة للتجزئة).
  • القيمة الخاصة null عضو في كل domain، وبتدل إن القيمة "unknown".
  • الـ null بتسبب تعقيدات في تعريف عمليات كتير.

Relations are Unordered

  • ترتيب الـ tuples غير مهم (ممكن تتخزن بأي ترتيب).

Schema vs Instance

  • Database schema: الهيكل المنطقي للـ DB.
  • Database instance: لقطة (snapshot) من البيانات في لحظة معينة.
  • مثال: schema = instructor(ID, name, dept_name, salary)، والـ instance = الجدول بالبيانات الفعلية.

Formal Definitions – Schema

  • Schema (أو الوصف) لـ Relation: بتتكتب R(A1, A2, ..., An)
    • R = اسم الـ relation
    • A1…An = attributes الـ relation
  • مثال: CUSTOMER (Cust-id, Cust-name, Address, Phone#)
    • CUSTOMER = اسم الـ relation
    • معرّفة على 4 attributes
    • كل attribute له domain (مجموعة قيم صالحة). مثلاً domain الـ Cust-id هو أرقام من 6 خانات.
  • Tuple: مجموعة مرتبة من القيم (بين أقواس زاوية < … >).
    • كل قيمة مشتقة من domain مناسب.
    • الصف في CUSTOMER هو 4-tuple (فيه 4 قيم). مثال:
<632895, "John Smith", "101 Main St. Atlanta, GA 30332", "(404) 894-2000">
  • الـ relation هو set من tuples (صفوف).
  • الـ domain له تعريف منطقي. مثال: "USA_phone_numbers" هي مجموعة أرقام التليفون ذات الـ 10 خانات الصالحة في أمريكا.
  • الـ domain له كمان data-type أو format:
    • USA_phone_numbers ممكن يكون format بتاعها: (ddd)ddd-dddd حيث d رقم عشري.
    • التواريخ لها formats مختلفة: yyyy-mm-dd أو dd mm,yyyy إلخ.

Characteristics Of Relations

  • ترتيب الـ tuples في relation r(R): الـ tuples غير مرتبة رغم إنها بتبان في شكل جدول.
  • ترتيب الـ attributes في الـ schema R (وترتيب القيم داخل كل tuple): بنعتبر الـ attributes في R(A1…An) والقيم في t=<v1, v2, ..., vn> مرتبة.
  • القيم داخل الـ tuple:
    • كل القيم atomic (indivisible).
    • كل قيمة لازم تكون من domain الـ attribute بتاع العمود.
    • لو t = <v1, v2, …, vn> هو tuple في relation state r لـ R(A1…An)، فكل vi لازم تكون قيمة من dom(Ai).
  • قيمة null الخاصة بتمثل القيم المجهولة أو غير المنطبقة على tuples معينة.
  • (مثال في الملف: جدول STUDENT — Name, Ssn, Home_phone, Address, Office_phone, Age, Gpa — وفيه قيم NULL.)

Relational Integrity Constraints

  • القيود = شروط لازم تتحقق في كل relation states الصالحة.
  • 3 أنواع رئيسية:
    • Key constraints
    • Entity integrity constraints
    • Referential integrity constraints
  • في قيد ضمني رابع: Domain constraint — كل قيمة في tuple لازم تكون من domain الـ attribute (أو null لو مسموح).

Superkey

  • مجموعة attributes اسمها SK في R بالشرط ده: مفيش tuples اتنين في أي relation state صالح r(R) ليهم نفس قيمة SK.
  • يعني لأي tuples مختلفين t1 و t2: t1[SK] ≠ t2[SK].
  • الشرط ده لازم يتحقق في أي valid state.

Key

  • هو "minimal" superkey.
  • أي: superkey K بحيث حذف أي attribute منه يخلي المجموعة اللي تتبقى مش superkey (مبقاش عندها خاصية الـ uniqueness).

مثال CAR

CAR(State, Reg#, SerialNo, Make, Model, Year)
  • CAR عنده مفتاحين (two keys): Key1 = {State, Reg#} ، Key2 = {SerialNo}
  • الاتنين برضه superkeys.
  • {SerialNo, Make} هو superkey لكن مش key (مش minimal).

بشكل عام

  • أي key هو superkey (لكن العكس مش صحيح).
  • أي مجموعة attributes تحتوي key هي superkey.
  • الـ minimal superkey هو key.

Primary Key

  • لو الـ relation له عدة candidate keys، بيتختار واحد بشكل اعتباطي يبقى primary key.
  • attributes الـ primary key بتتحط تحتها خط (underlined).
  • مثال: CAR(State, Reg#, SerialNo, Make, Model, Year) اخترنا SerialNo كـ primary key.
  • قيمة الـ primary key بتستخدم لتحديد كل tuple بشكل فريد (بتوفر هوية الـ tuple).

Entity Integrity

  • attributes الـ primary key (PK) لكل relation schema R مينفعش يبقى فيها null في أي tuple.
  • السبب: قيم الـ PK بتستخدم لتحديد الـ tuples الفردية.
  • t[PK] ≠ null لأي tuple t.
  • لو الـ PK فيه أكتر من attribute، null غير مسموح في أي واحد منهم.
  • ملحوظة: attributes تانية في R ممكن تتقيد برضه بعدم قبول null حتى لو مش جزء من الـ PK.

Referential Integrity

  • قيد بيتعلق بـ relation اتنين (القيود السابقة كانت على relation واحد).
  • بيحدد علاقة بين tuples في relation اتنين: referencing relation و referenced relation.
  • الـ tuples في referencing relation R1 ليها attributes FK (foreign key) بتشير لـ primary key attributes PK في referenced relation R2.
  • الـ tuple t1 في R1 بيشير لـ tuple t2 في R2 لو t1[FK] = t2[PK].
  • نص القيد: قيمة الـ FK في الـ referencing relation R1 ممكن تكون إما:
    • (1) قيمة موجودة فعلاً كـ primary key في الـ referenced relation R2، أو
    • (2) null.
  • في الحالة (2): الـ FK في R1 مينفعش يكون جزء من الـ primary key بتاعه.

Displaying a relational database schema

  • كل relation schema بيتعرض كـ صف من أسماء الـ attributes.
  • اسم الـ relation بيتكتب فوق أسماء الـ attributes.
  • الـ primary key attribute(s) تحتها خط.
  • الـ foreign key (referential integrity) بيتعرض كـ سهم موجه (directed arc) من attributes الـ FK للجدول المشار إليه.
  • ممكن كمان يشاور على الـ primary key للجدول المشار إليه للتوضيح.
  • (في الملف: Figure 5.7 لـ COMPANY schema: EMPLOYEE, DEPARTMENT, DEPT_LOCATIONS, PROJECT, WORKS_ON, DEPENDENT. وكمان schema diagram للـ University: takes, student, section, course, department, advisor, time_slot, prereq, instructor, classroom, teaches.)

Relational Algebra

  • لغة جبرية مكونة من مجموعة عمليات بتاخد relation أو اتنين كمدخل وبتنتج relation جديد كنتيجة.

Select Operation (σ)

  • بيختار الـ tuples اللي بتحقق predicate معين.
  • الرمز: σp(r) — الـ p اسمه selection predicate.
  • مثال: σ dept_name="Physics" (instructor) ← النتيجة: Einstein و Gold.
  • مسموح بمقارنات: =, ≠, >, <, ≥, ≤ في الـ predicate.
  • ممكن ندمج predicates بـ connectives: ∧ (and)، ∨ (or)، ¬ (not).
  • مثال: مدرسين الفيزياء بمرتب أكبر من 90,000:
σ dept_name="Physics" ∧ salary>90,000 (instructor)
  • الـ predicate ممكن يشمل مقارنة بين attributes اتنين. مثال: كل الأقسام اللي اسمها نفس اسم المبنى:
σ dept_name=building (department)

Project Operation (π)

  • عملية unary أساسية بتختار أعمدة (attributes) معينة من جدول وبترمي الباقي.
  • بتعمل vertical partitioning للـ relation وبترجع جدول جديد فيه الحقول المطلوبة بس.
  • النتيجة = relation فيه k عمود بعد مسح الأعمدة غير المذكورة.
  • الصفوف المكررة بتتشال من النتيجة لأن relations هي sets.
  • مثال: إلغاء dept_name من instructor:
π ID, name, salary (instructor)

Composition of Relational Operations

  • نتيجة أي عملية relational algebra هي relation، وعشان كده العمليات ممكن تتركب مع بعض في expression.
  • مثال: أسماء كل مدرسين قسم Physics:
π name ( σ dept_name="Physics" (instructor) )
  • ← النتيجة: Einstein, Gold
  • بدل ما نكتب اسم relation كـ argument للـ projection، بنكتب expression بيقيّم لـ relation.

Cartesian Product (×)

  • بيسمح بدمج معلومات من أي relation اتنين.
  • مثال: instructor × teaches
  • بنبني tuple في النتيجة من كل زوج ممكن من الـ tuples: واحد من instructor وواحد من teaches.
  • الـ attributes المشتركة (زي ID) بتتسمى بـ instructor.ID و teaches.ID.

Join Operation (⋈)

  • بيدمج عملية select مع Cartesian Product في عملية واحدة.
  • لو r(R) و s(S) و θ predicate على attributes في schema R ∪ S:
r ⋈θ s = σθ (r × s)
  • مثال: σ instructor.id = teaches.id (instructor × teaches)
  • ممكن تتكتب بشكل مكافئ: instructor ⋈ instructor.id = teaches.id teaches

Union Operation (∪)

  • بيدمج relations اتنين. الرمز: r ∪ s
  • شروط صلاحية r ∪ s:
    • r و s لازم يكون لهم نفس الـ arity (نفس عدد الـ attributes).
    • الـ domains لازم تكون compatible (مثلاً العمود التاني في r من نفس نوع قيم العمود التاني في s).
  • مثال: course_id لكورسات Fall 2017 ∪ كورسات Spring 2018 ← CS-101, CS-315, CS-319, CS-347, FIN-201, HIS-351, MU-199, PHY-101 (بدون تكرار).

Set Intersection (∩)

  • بيلاقي الـ tuples الموجودة في الـ relation الاتنين. الرمز: r ∩ s
  • افتراض: r, s نفس الـ arity وattributes متوافقة.
  • مثال: كورسات اتدرست في Fall 2017 و Spring 2018 معاً:
π course_id (σ semester="Fall" ∧ year=2017 (section))
 ∩
π course_id (σ semester="Spring" ∧ year=2018 (section))
  • ← النتيجة: CS-101

Set Difference (−)

  • بيلاقي الـ tuples الموجودة في relation ومش موجودة في التاني. الرمز: r − s
  • لازم بين relations متوافقة: نفس الـ arity و domains متوافقة.
  • مثال: كورسات Fall 2017 لكن مش Spring 2018:
π course_id (σ semester="Fall" ∧ year=2017 (section))
 −
π course_id (σ semester="Spring" ∧ year=2018 (section))
  • ← النتيجة: CS-347, PHY-101

Assignment Operation (←)

  • مفيد أحياناً نكتب expression بـ إسناد أجزاء منه لمتغيرات relation مؤقتة.
  • بيتكتب بسهم ← وبيشتغل زي الـ assignment في لغات البرمجة.
  • مثال: كل المدرسين في Physics و Music:
Physics ← σ dept_name="Physics" (instructor)
Music   ← σ dept_name="Music" (instructor)
Physics ∪ Music
  • بالـ assignment، الـ query ممكن تتكتب كـ برنامج تسلسلي من إسنادات يتبعها expression قيمته بتتعرض كنتيجة.

Aggregate Functions (γ)

  • متوسط مرتبات المدرسين: γ avg(salary) (instructor)
  • إجمالي عدد الكورسات في 2018: γ count(course_id) (σ year=2018 (section))
  • متوسط المرتب في كل قسم (grouping): dept_name γ avg(salary) (instructor)
  • النتيجة: Biology 72000، Comp. Sci. 77333، Elec. Eng. 80000، Finance 85000، History 61000، Music 40000، Physics 91000.

Equivalent Queries

  • في أكتر من طريقة لكتابة query في relational algebra.
  • مثال: معلومات الكورسات اللي بيدرّسها مدرسو Physics بمرتب أكبر من 90,000:
Query 1: σ dept_name="Physics" ∧ salary>90,000 (instructor)
Query 2: σ dept_name="Physics" ( σ salary>90,000 (instructor) )
  • الـ queries مش متطابقة (not identical) لكنها متكافئة (equivalent) — بتدي نفس النتيجة على أي database.

select name from instructor

  • الـ query ممكن تحتوي حتى 6 clauses، لكن الأولين بس إجباريين: SELECT و FROM. الترتيب:
SELECT    <attribute list>
FROM      <table list>
[WHERE    <condition>]
[GROUP BY <grouping attribute(s)>]
[HAVING   <group condition>]
[ORDER BY <attribute list>]
  • SELECT: الـ attributes أو الدوال المراد استرجاعها.
  • FROM: كل الـ relations (أو aliases) المطلوبة في الـ query لكن مش المطلوبة في nested queries.
  • WHERE: شروط الاختيار والـ join للـ tuples.
  • GROUP BY: attributes التجميع.
  • HAVING: شرط لاختيار الـ groups.
  • ORDER BY: ترتيب عرض النتيجة.
  • ترتيب تقييم الـ query: أول حاجة WHERE، بعدين GROUP BY و HAVING، وأخيراً SELECT.

Views in SQL

  • الـ view هو جدول "افتراضي" (virtual) مشتق من جداول تانية.
  • بيسمح بعمليات update محدودة (لأن الجدول ممكن مايكونش مخزن فيزيائياً).
  • بيسمح بعمليات query كاملة.
  • صيغة Create View:
CREATE VIEW <view name> AS <view-defining-expression (query)>
[WITH CHECK OPTION];
  • الـ WITH CHECK OPTION لازم تتحدد لو الـ view هيتعدل، عشان النظام يتحقق من view updatability.
  • مثال (جدول WORKS_ON جديد):

FROM EMPLOYEE, PROJECT, WORKS_ON

GROUP BY PNAME;

View Update

  • update على view واحد من غير aggregate operations: ممكن يتحول لـ update على الـ base table الأساسي.
  • Views فيها joins: الـ update ممكن يتحول لـ update على الـ base relations الأساسية.

Advantages of Using Views (مميزات الـ Views)

  • الـ views ممكن تمثل subset من البيانات الموجودة في جدول.
  • الـ view بيحدد درجة تعرض الجداول الأساسية للعالم الخارجي: المستخدم ممكن يبقى له صلاحية يعمل query على الـ view بينما ممنوع من باقي الـ base table.
  • الـ views بتدمج وتبسط عدة جداول في جدول افتراضي واحد.
  • الـ views ممكن تعمل كجداول مجمّعة (aggregated): الـ DB engine بيجمع البيانات (sum, average…) ويعرض النتائج المحسوبة كجزء من البيانات.
  • الـ views بتخبي تعقيد البيانات.
  • الـ views بتاخد مساحة تخزين قليلة جداً: الـ DB بتحتوي تعريف الـ view بس، مش نسخة من كل البيانات اللي بيعرضها.
  • الـ views بتوفر أمان إضافي.

Definition of "some" Clause

التعريف 
F <comp> some r  ⇔  ∃ t ∈ r such that (F <comp> t)

حيث <comp> ممكن تكون: <, ≤, >, =, ≠

  • الـ some بتستخدم لمقارنة قيمة واحدة (F) بمجموعة (relation r) راجعة من subquery.
  • التعبير بيبقى true لو شرط المقارنة اتحقق على عنصر واحد على الأقل (t) في المجموعة.
التعبيرالنتيجةالتفسير
5 < some {0, 5, 6}true5 < 6 فيه عنصر واحد حقق الشرط
5 < some {0, 5}false5 مش أصغر من 0 ولا من 5
5 = some {0, 5}true5 بتساوي 5 اللي جوه المجموعة
5 ≠ some {0, 5}true5 ≠ 0 فيه عنصر واحد حقق الشرط
  • (= some) ≡ in

  • exists r ⇔ r ≠ Ø
  • not exists r ⇔ r = Ø

Use of "exists" Clause

  • طريقة تانية لكتابة: "الكورسات اللي اتدرست في Fall 2017 و Spring 2018":
select course_id
from section as S
where semester = 'Fall' and year = 2017 and
      exists (select *
              from section as T
              where semester = 'Spring' and year= 2018
                    and S.course_id = T.course_id);
  • Correlation name: المتغير S في الـ outer query.
  • Correlated subquery: الـ inner query.

Use of "not exists" Clause

  • كل الطلاب اللي أخدوا كل الكورسات المقدمة في قسم Biology:
select distinct S.ID, S.name
from student as S
where not exists ( (select course_id
                    from course
                    where dept_name = 'Biology')
                   except
                   (select T.course_id
                    from takes as T
                    where S.ID = T.ID));
  • الـ nested query الأولى: بتجيب كل كورسات Biology.
  • الـ nested query التانية: بتجيب كل الكورسات اللي طالب معين أخدها.
  • ملحوظة: X – Y = Ø ⇔ X ⊆ Y
  • ملحوظة: مينفعش نكتب الـ query دي باستخدام = all وصيغها.

Test for Absence of Duplicate Tuples

  • الـ unique بتختبر لو الـ subquery فيها tuples مكررة في نتيجتها.
  • بتدي true لو الـ subquery مفيهاش تكرار.
  • مثال: كل الكورسات اللي اتقدمت مرة واحدة على الأكتر في 2017:
select T.course_id
from course as T
where unique (select R.course_id
              from section as R
              where T.course_id= R.course_id
                    and R.year = 2017);

Subqueries in the From Clause

  • SQL بتسمح باستخدام subquery في الـ from clause.
  • متوسط مرتبات المدرسين في الأقسام اللي متوسط مرتبها أكبر من $42,000:
select dept_name, avg_salary
from ( select dept_name, avg (salary) as avg_salary
       from instructor
       group by dept_name)
where avg_salary > 42000;
  • ملحوظة: مش محتاجين نستخدم having clause.
  • طريقة تانية لكتابة نفس الـ query (بإعادة تسمية الجدول والـ attributes):
select dept_name, avg_salary
from ( select dept_name, avg (salary)
       from instructor
       group by dept_name)
       as dept_avg (dept_name, avg_salary)
where avg_salary > 42000;

With Clause

  • الـ with clause بتوفر طريقة لتعريف relation مؤقتة تعريفها متاح بس للـ query اللي فيها الـ with.
  • مثال: كل الأقسام اللي ليها أقصى ميزانية:
with max_budget (value) as
     (select max(budget)
      from department)
select department.name
from department, max_budget
where department.budget = max_budget.value;

Complex Queries using With Clause

  • كل الأقسام اللي إجمالي المرتبات فيها أكبر من متوسط إجمالي المرتبات في كل الأقسام:
with dept_total (dept_name, value) as
     (select dept_name, sum(salary)
      from instructor
      group by dept_name),
     dept_total_avg(value) as
     (select avg(value)
      from dept_total)
select dept_name
from dept_total, dept_total_avg
where dept_total.value > dept_total_avg.value;

Modification of the Database

  • Deletion لـ tuples من relation معينة.
  • Insertion لـ tuples جديدة في relation معينة.
  • Updating لقيم في بعض الـ tuples في relation معينة.

Deletion

  • مسح كل المدرسين:
delete from instructor
  • مسح كل مدرسي قسم Finance:
delete from instructor
where dept_name= 'Finance';
  • مسح كل tuples المدرسين المرتبطين بقسم موجود في مبنى Watson:
delete from instructor
where dept_name in (select dept_name
                    from department
                    where building = 'Watson');
  • مسح كل المدرسين اللي مرتبهم أقل من متوسط مرتبات المدرسين:
delete from instructor
where salary < (select avg (salary)
                from instructor);
  • المشكلة: كل ما بنمسح tuples من instructor، متوسط المرتب بيتغير.
  • الحل المستخدم في SQL:
    • 1) الأول نحسب avg (salary) ونلاقي كل الـ tuples اللي هتتمسح.
    • 2) بعدين نمسح كل الـ tuples اللي لقيناها (من غير ما نعيد حساب avg أو نعيد اختبار الـ tuples).

Insertion

  • إضافة tuple جديد لجدول course:
insert into course
      values ('CS-437', 'Database Systems', 'Comp. Sci.', 4);
  • أو بشكل مكافئ (بتحديد أسماء الـ attributes):
insert into course (course_id, title, dept_name, credits)
      values ('CS-437', 'Database Systems', 'Comp. Sci.', 4);
  • إضافة tuple لجدول student مع tot_creds = null:
insert into student
      values ('3003', 'Green', 'Finance', null);
  • خلّي كل طالب في قسم Music خد أكتر من 144 credit hour يبقى مدرس في قسم Music بمرتب $18,000:
insert into instructor
      select ID, name, dept_name, 18000
      from   student
      where  dept_name = 'Music' and total_cred > 144;
  • جملة select from where بتتقيّم بالكامل قبل ما أي من نتايجها تتضاف للـ relation.

Updates

  • زيادة 5% في مرتب كل المدرسين:
update instructor
   set salary = salary * 1.05
  • زيادة 5% للمدرسين اللي مرتبهم أقل من 70000:
update instructor
   set salary = salary * 1.05
   where salary < 70000;
  • زيادة 5% للمدرسين اللي مرتبهم أقل من المتوسط:
update instructor
   set salary = salary * 1.05
   where salary < (select avg (salary)
                   from instructor);
  • زيادة مرتبات اللي فوق $100,000 بنسبة 3%، وكل الباقي 5%. بنكتب two update statements:
update instructor
   set salary = salary * 1.03
   where salary > 100000;
update instructor
   set salary = salary * 1.05
   where salary <= 100000;
  • الترتيب مهم! لو عكسنا الترتيب، مدرس ممكن ياخد الزيادتين.

Case Statement for Conditional Updates

  • نفس الـ query اللي فاتت بس باستخدام case statement (في update واحد وبدون مشكلة الترتيب):
update instructor
   set salary = case
                  when salary <= 100000 then salary * 1.05
                  else salary * 1.03
                end
